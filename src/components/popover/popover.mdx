### Popover vs. Tooltip vs. Dialog

| Component | Trigger | Interactive content | Blocks the page |
| --------- | ------- | ------------------- | --------------- |
| `Tooltip` | Hover or focus | No | No |
| `Popover` | Click | Yes | No |
| `Dialog`  | Click | Yes | Yes — modal with a scrim |

### Accessibility

The surface uses `role="dialog"`, which must have an accessible name — so exactly one of `title` (rendered as a heading) or `aria-label` is **required**, and TypeScript enforces it. The trigger receives `aria-haspopup="dialog"`, `aria-expanded`, and `aria-controls`.

`title` renders as an `h2` by default. Set `headingLevel` to keep the surrounding document outline correct, since the library cannot know where in the page the popover sits.

The trigger element is cloned rather than wrapped, so a `button` is ideal. A non-interactive host element such as a `span` also receives `role="button"` and `tabIndex={0}` so it stays keyboard operable, and anything that is not a React element is wrapped in a `button` automatically.

Opening moves focus to the first focusable element inside the popover, or to the surface itself when it holds no controls — where a focus ring makes the landing point visible. Escape closes it and returns focus to the trigger, but only when the popover held focus, so a dismissal never yanks focus from elsewhere on the page. The popover is non-modal and never traps focus: tabbing past the last control (or back past the first) closes it and hands focus to the trigger, letting the browser carry on from there. That is what keeps a portalled surface — appended to `document.body`, far from its trigger — from stranding focus at the end of the document.

### Collision handling

With `usePortal`, placement is measured against the viewport: the popover flips to the opposite side when the requested one can't fit, and is clamped along its cross axis so it never runs off screen — the arrow follows the surface so it keeps pointing at the trigger. A flip only happens when the opposite side genuinely has more room, so a popover squeezed on both sides stays where you asked for it.

Without `usePortal` the popover is positioned by CSS relative to its trigger, which means it tracks the trigger through layout and scrolling for free but cannot collision-detect. That is the trade: reach for `usePortal` when the trigger sits near a viewport edge, or when an ancestor clips overflow.

### Known limitations

Screen-reader users encounter a portalled surface at the end of the document rather than next to its trigger, which is the other reason `usePortal` defaults to `false`.
